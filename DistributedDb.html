Overview

Features of distributed databases

Spreading data out brings speed and reliability, but it creates problems too. Each feature below either brings a benefit or solves one of those problems. Tap a card to jump to its simulation.

The big challengeWhen data is in several places, how do we keep every copy the same? Inconsistent data leads to wrong information, bad decisions, conflicting records and a loss of data integrity.
Feature · Data partitioning 데이터 분할

Cut the table into fragments

Partitioning divides the database into smaller parts (fragments) and stores them on different nodes. Choose how to cut TicketWave's Members table.

Reasons to partitionBetter performance (each node searches a smaller data set, close to its users) · higher availability (if one fragment's node fails, the others still work) · large data sets are easier to manage.
Stretch

Vertical fragments must each keep the primary key (member_id). Without it, the system cannot join the fragments back into the original rows. Horizontal fragments must together contain every row exactly once, so that no data is lost or duplicated.

Feature · Replication 복제 + data consistency

Three copies of the seat count

Replication keeps copies of the same data on several nodes. Here every node holds the number of seats left. Sell a ticket in Seoul and watch how the copies catch up.

Replication mode
SynchronousAsynchronous
When is the write confirmed?After every copy is updatedStraight away; copies update later
ConsistencyHigh: all copies always matchCopies can be out of date (stale) for a short time
Latency (waiting time)High: waits for the slowest nodeLow
If one node is unreachableWrites are blockedWrites continue; that node catches up later
Good forBank balances, ticket seatsSocial media likes, view counts

Trade-off: strong consistency or low latency. You cannot fully have both, so the choice depends on what the application needs.

Stretch

Consensus means the nodes agree on the current state of the data. Quorum is one way to reach it: an operation succeeds when a majority of nodes (here 2 of 3) confirm it. This is faster than waiting for all nodes and still survives one node failing.

A common rule is W + R > N: if a write goes to W nodes and a read asks R nodes, out of N copies, then every read overlaps at least one up-to-date copy. With N = 3, W = 2, R = 2 the rule holds.

Feature · Concurrency control 동시성 제어

Two fans, one seat left

Concurrency control manages many users using the database at the same time. Minji (Seoul) and Joon (Busan) both try to buy the last seat. Step through what happens with each method.

LockingA transaction locks the data before changing it. Other transactions must wait until the lock is released.
TimestampsEach transaction gets a timestamp when it starts. Conflicts are settled by timestamp order; a transaction that breaks the order is aborted and restarted.
Stretch

Deadlock: Minji locks seat A and waits for seat B, while Joon locks seat B and waits for seat A. Neither can continue. Systems detect this and abort one transaction. Timestamp methods avoid deadlock because nobody waits for a lock, but more transactions get aborted and restarted.

Stretch

Two-phase commit (2PC) gives atomicity across nodes. Phase 1 (prepare): a coordinator asks every node "can you commit?" and each node votes. Phase 2 (commit): only if all vote yes does the coordinator tell everyone to commit; one "no" or no reply means everyone rolls back. The ACID button above runs this.

Features · Distribution transparency 분산 투명성 + global query processing

It looks like one table

Distribution transparency hides the nodes from users and applications. They use the database as if it were one centralised system. Behind the scenes, global query processing decides how to fetch the data from the nodes.

Query
What the user writes (from Seoul)

No node names, no locations. The same SQL would work on a centralised database.

What the system does · choose a plan
Location transparency

Users do not need to know where the data is stored. The system finds it.

Fragmentation transparency

Users do not know the table is split into fragments. They query the whole table.

Access transparency

Local and remote data are accessed in exactly the same way.

Benefit: programmers write simpler applications and users get a smoother experience. Global query processing aims to cut network traffic and response time.

Features · Scalability 확장성 + fault tolerance 결함 허용

Horizontal: add more machines

Fault toleranceThe system keeps working correctly even when hardware or software fails. It is achieved with replication (several copies of data), redundant hardware and software, and failover (another node automatically takes over). You saw this in the Big picture: crash a node in Distributed mode.
Scalability in examsHorizontal scaling is the usual choice for distributed databases. It has almost no upper limit, and extra nodes add fault tolerance. Vertical scaling hits a hardware limit and leaves one point of failure.
Feature · Data security 데이터 보안

More places to attack

Data spread across many locations means more nodes and more network links to protect.

Data travelling from Busan to Seoul

Authentication and authorisation

Check who you are and what you may do, at every node, not just one.

Encryption

In transit (moving between nodes) and at rest (stored on each node's disks).

Auditing and monitoring

Log who accessed what and when, on every node, and watch for unusual access.

Consistent policies

Every node follows the same security rules. One weak node puts all the data at risk.
